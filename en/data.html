1 Training data

The model learns from past declarations stored in the Sirene register. Each observation contains:

  • the activity description: free text typed by the declarant, sometimes followed by details on secondary or agricultural activity;
  • auxiliary variables from the declaration form:
    • the legal form (CJ, catégorie juridique);
    • the nature of the activity (NAT);
    • the type of form (TYP);
    • the surface area of the premises (SRF, grouped into bins);
    • whether the activity is permanent or seasonal (CRT);
  • the APE code that was assigned, either automatically or by a human coder.

The earliest models were trained on about 10 million declarations from the former register (2014–2022). Since the move to the new register and to NAF 2025, the training base is built from about 2.7 million recent declarations (Randriamanana and Faria 2025).

WarningLabels are not ground truth

Historical labels come from Sicore, from earlier versions of the model and from human coders working under time pressure. Some are wrong, and some contradict each other: the same description can carry different codes. Label quality matters as much as model architecture. Two components address it: the rule engine (below) and the annotation campaigns (Monitoring).

2 Label cleaning: an auditable rule engine

codif-ape-preprocess applies business rules to the training data before every training run. A rule turns knowledge from business experts into code. For example, furnished-rental activities described with the acronym “LMNP”, holding companies, ride-hailing drivers and taxis each go to a precise code.

Rules can do three things:

Rules are Python functions registered with a decorator. Each one carries a name, tags and a description. A rule matches descriptions using one or more of three methods:

  • regular expressions on normalised text;
  • fuzzy matching, to absorb typos;
  • semantic similarity, using a sentence-embedding model computed on GPU.

Fuzzy and semantic matching widen a rule to descriptions that are close to the ones the experts listed. Each rule decides which methods it allows. For instance, a rule on a short acronym is restricted to exact matching.

The rule engine therefore has two parts, which are not judged the same way:

  • the deterministic part (exact patterns validated by experts) encodes the known cases, written \(K_n\) in the retraining protocol. It is checked like a unit test: the model must reproduce it;
  • the probabilistic part (fuzzy and semantic extensions) makes a guess on descriptions that no expert has seen. It is an automatic coding engine in its own right, and its precision must be measured before its labels are trusted.

Every change is logged. For each modified, created or deleted row, a journal records the code before and after, the rule that applied and the context of the declaration. These journals are stored next to the cleaned dataset, so any label in the training set can be traced back to its origin.

Rules are what make expert feedback permanent. If an error is fixed only by retraining, it can come back with the next model. A rule, on the other hand, fixes the whole training set for good, and the fix can be audited. How rules are created, checked and propagated is described in the retraining protocol.

3 Splits and versioning

After cleaning, the pipeline:

  1. builds the final features: the description joined with its complementary text fields, and the categorical variables;
  2. splits the data into training, validation and test sets;
  3. writes the splits to S3 in a folder named after the extraction date;
  4. records this folder, along with the list of features, in a shared configuration file read by the training code.

Every training run logs its input datasets in MLflow. The run is therefore tied to an exact snapshot of the data.

4 Moving to NAF 2025

The European revision of the activity classification (NACE Rev. 2.1, called NAF 2025 in France) takes effect for all Sirene units on 1 January 2027. The model must be trained on a classification that no historical data was labelled in.

4.1 The correspondence problem

The official correspondence table between NAF rev. 2 and NAF 2025 links 732 old sub-classes to 746 new ones (Randriamanana and Faria 2025):

Randriamanana, Nathan, and Thomas Faria. 2025. Changement de Nomenclature Statistique à l’ère Du Machine Learning : Réentraînement Basé Sur Les LLM Pour La Révision de La NAF. Journées de méthodologie statistique (JMS). https://inseefrlab.github.io/codif-ape-prez/papers/jms2025-llm-relabeling/index.pdf.
  • 551 univocal correspondences: the old code maps to a single new code, so translation is mechanical;
  • 181 multivocal correspondences: the old code splits into several new codes (up to 38), and the description must be read to choose.

Multivocal codes are only 25 % of codes, but they cover 52 % of training observations, about 1.4 million rows. Business experts first requalified some “false multivocals” (cases where one target clearly dominates). This settled about a third of them. Around 500,000 observations still had to be recoded one by one.

4.2 Experts as the benchmark, LLMs as the scale

The recoding combined human expertise with large language models:

  1. Expert annotation. About 25 business experts annotated around 30,000 multivocal descriptions in NAF 2025, using Label Studio, over roughly five months. The campaign also produced inter-annotator agreement figures, which set a realistic ceiling: three independent experts agree on the sub-class in only about 62 % of cases, while at least two of them agree in 96 % of cases.
  2. LLMs as virtual annotators. Open-weight LLMs, served on the platform with vLLM, recoded the multivocal observations (codif-ape-nace-revision). Each prompt contained the description, the candidate NAF 2025 codes and their explanatory notes (context-augmented generation). The output was constrained to a JSON schema. Several models were compared against the expert annotations. The best single model reached about 72 % accuracy at the sub-class level, and combining models by vote or cascade added a few points.
  3. Business rules were then applied on top, through the rule engine, to fix systematic errors.

In the end, about 2.3 million of the 2.7 million observations were rebuilt in NAF 2025. Later iterations, using more recent open-weight models and majority voting, raised LLM accuracy to about 78 % (Pramil 2026).

Pramil, Julien. 2026. When Classifications Change but Deadlines Don’t: Scaling Recoding with LLMs. The NACE Transition at Insee. ISI World Statistics Congress, Malta. https://inseefrlab.github.io/codif-ape-prez/slides/isi-malta-relabeling/.
TipLesson

Expert annotations are expensive, so they are best used as a benchmark. They guide the choice of prompts and models and measure the result, while LLMs supply the volume. An LLM’s self-reported confidence turned out to be an unreliable filter. Agreement between several models is a better signal.

The model retrained on these data is described in the Model chapter.

5 GRAAL

GRAAL (documentation), Graph-based Reasoning Agents for Automatic Labelling, is a framework of LLM agents for coding free text into a hierarchical classification. It rests on two building blocks:

  1. the explanatory notes as a graph, stored in the Neo4j graph database (Neo4j, Inc. 2026);
  2. tools to interact with this graph, made available to LLMs.
Neo4j, Inc. 2026. Neo4j: Graph Database. https://neo4j.com/docs/.

Like torchTextClassifiers, it was born from the needs of APE coding and is developed as a general-purpose, open-source tool. Unlike it, GRAAL sits off the critical path: it works offline, on data rather than on live requests. It belongs in this chapter because what it produces is labels.

5.1 Principle

The graph. The full explanatory notes are loaded into Neo4j:

  • codes and labels;
  • explanatory notes: includes, excludes, examples;
  • parent–child relations, plus a vector index on the notes.

The tools. LLMs reach the graph only through tools: move down or up the hierarchy, read a code’s notes, find the notes closest to a text. This lets them browse the classification the way a human expert would. The agents described below are different ways of combining these tools. All inputs and outputs are typed Pydantic contracts. The agents run against any OpenAI-compatible endpoint, served on the platform with open-weight models.

Because all classification knowledge lives in the graph, the framework is independent of the classification. Graphs exist for NAF 2025 (French), NACE Rev. 2.1 (English) and COICOP 2018.

5.2 Components

GRAAL also includes an evaluation module and review applications in which experts judge the agents’ verdicts. The evaluation module offers metrics at each level, stratified samples with weights, bootstrap confidence intervals and paired tests.

5.3 Role in the pipeline

GRAAL does not replace the production model. The agents take seconds to minutes per description and need GPUs to serve the LLM, while production needs ~200 ms on CPU. In early benchmarks, the agents were also not more accurate than the supervised model on the flow as a whole. GRAAL’s value lies elsewhere, in four offline tasks:

  1. Recoding a stock after a classification change. Most of the NAF 2025 training data was produced by a dedicated pipeline, codif-ape-nace-revision, in which LLMs code with the explanatory notes in context (above). GRAAL generalises this approach with agents that navigate the classification, for future revisions and other classifications.
  2. Auditing and curating labels. The MatchVerifier flags dubious labels in the training data, or in automatically coded cases, and proposes alternatives. In the retraining protocol, GRAAL is one of the independent engines whose disagreements with the production model are arbitrated.
  3. Prioritising human review. Suspicious cases are sent to experts first. Their judgements are collected in a review application and become new labels.
  4. Generating synthetic data. Code2Text produces descriptions for rare codes (see below), and reworded variants of known cases to test that a fix generalises.

In return, GRAAL relies on the production API. It uses the API as a supervised baseline, and as a source of candidate codes for agents and annotators.

5.4 Labels from engines must be earned

GRAAL and the probabilistic part of the rule engine play the same role: they propose labels that no human has checked. Before either one feeds training, it is evaluated where it matters, on the cases where it disagrees with the production model, against the golden set. The criterion and its precautions are set out in the retraining protocol and the Evaluation chapter.

6 Synthetic data: Code2Text

Matéo Morin’s internship (ENSAE Paris, Innovation Lab, 2026) studied how to generate synthetic activity descriptions with LLMs for NAF 2025. It builds on GRAAL’s Code2Text agent (GRAAL). The report, slides and appendices are online at mateomorin.github.io/Code2Text-presentation (in French). This is exploratory work.

6.1 Why synthetic data

Two needs drive this work:

  • the long tail: in a training file of more than a million descriptions, half the codes have fewer than 60 examples. The model learns these codes poorly;
  • statistical confidentiality: declarations cannot be released, whether for teaching, hackathons or research. A faithful synthetic dataset could be.

The two uses call for different code distributions. Release must reproduce the real distribution; training benefits from over-representing rare codes. Generation is therefore done code by code: once the generated descriptions for a code look like the real descriptions of that code, choosing how many to draw per code serves either use.

6.2 A first generation from the explanatory notes

NaiveCode2Text gives the LLM, for each code, its title, some of its inclusions, all its exclusions and a few real descriptions of the same code (few-shot). Requests run in parallel: 62,100 descriptions covering the whole classification were produced in 42 minutes.

The descriptions are correct in substance but too clean: no typos, formal, often close to the code’s title. For forestry, for example, the model writes “Activités forestières : culture de peupliers et de saules” (forestry activities: growing poplars and willows). Asking for a less formal style in the prompt changes nothing.

6.3 Measuring the LLM’s fingerprint: LabelGuard

LabelGuard is a discriminator that tells a human description from a generated one. It is a multilayer perceptron on Qwen3-Embedding-8B embeddings, trained on 160,000 descriptions, half real and half synthetic. Artefacts specific to the real data (descriptions truncated at 140 characters, numbers, a suffix added during preprocessing) were removed first, so that it learns style rather than these marks.

On 40,000 validation descriptions, LabelGuard reaches 99.4% accuracy, with a 0.7% false-positive rate. LLM style is thus almost perfectly recognisable. For the classifier, this is a distribution shift: trained on these descriptions, it does not see the same text as in production, where descriptions are abbreviated, choppy and full of typos.

6.4 Rewriting the style: Code2ReText

A first attempt gave LabelGuard to the generating LLM as a tool. The LLM cheated: it concatenated words, wrote unintelligible words and copied the descriptions that passed the test.

The final version, Code2ReText, splits two roles (orchestrated with LangGraph):

  • the Actor generates descriptions as NaiveCode2Text does, then rewrites them. It may change the form, not the substance;
  • the Supervisor receives LabelGuard’s scores and real descriptions of the same code. It instructs the Actor to rewrite the descriptions judged artificial (score above 0.70), without passing the real descriptions on.

The loop stops after at most five rounds. LabelGuard’s mean score drops with each round. For forestry, the model now writes for example “TRANSPLANTATION ARBRES” (tree transplanting).

6.5 Results

The protocol fixes a classifier whose hyperparameters are tuned on real data. It is trained on sets of 50,000 descriptions, a share \(\alpha\) of which is synthetic, then evaluated on 30,000 real descriptions. The sets are nested: the synthetic descriptions used for one value of \(\alpha\) are included in those of the next, and every code appears at least once. Differences between two values of \(\alpha\) therefore do not come from sampling.

  • Overall accuracy. It holds up to about 50% synthetic data and collapses beyond 90%.
  • By code frequency. On frequent codes, nothing changes. On mid-frequency codes, accuracy declines as \(\alpha\) grows. On rare codes, it improves markedly from the first injections, especially with Code2ReText. The chosen trade-off is 40 to 50% Code2ReText descriptions, drawn with a code distribution close to the real one.
  • Style and diversity. For almost every code, Code2ReText is closer to the real descriptions than NaiveCode2Text (Wasserstein distance between embeddings). In return, its diversity (DC-Score) collapses, while NaiveCode2Text’s slightly exceeds that of the real data. The approach cannot achieve both.
  • Leaks. About 0.5% of Code2ReText’s descriptions are copies of real descriptions, against 0.005% for NaiveCode2Text. The Actor and Supervisor found another way to fool LabelGuard. As it stands, this rules out release.

The study uses 50,000 descriptions, not the million of the full base. It also inherits the noise in the real labels (see above). The next step is to fine-tune a small open-weight model on the declarants’ style, rather than correct it with prompt loops. The same model could generate descriptions for NACE in several languages.

TipLesson

Synthetic descriptions complement real data on rare codes; they do not replace it. An LLM leaves a measurable style fingerprint, which must be checked before any injection. A generator optimised against a discriminator ends up copying its examples: before any release, check that no real description has leaked.
