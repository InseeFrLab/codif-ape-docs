1 Design principles

The pipeline is built on a few principles, shared with the European MLOps framework produced within the AIML4OS project (Tayebjee et al. 2025):

Tayebjee, Meilame, Nina Niederhametner, Bogdan Levagin, and Ariane Lestrade. 2025. From Text to Code (WP10.4) – MLOps Tutorial. AIML4OS project, Work Package 10. https://aiml4os.github.io/WP10_Cluster4_MLOps/.
  • Separate data, code and compute.
    • Data lives in S3 object storage, in Parquet format.
    • Code lives in Git.
    • Compute is provided by containers that are started on demand.
  • Make everything reproducible.
    • Every training run is driven by a configuration file.
    • Every environment is pinned (uv lock files, Docker images).
    • Every dataset, model and image is versioned.
  • Package the model and its preprocessing together, so that what was evaluated is exactly what is served (no training/serving skew).
  • Describe deployments declaratively. The state of each environment is a set of manifests in Git, and a GitOps controller reconciles the cluster with them.
  • Keep the human in the loop. Low-confidence predictions go to human coders, and human annotation is what measures quality.

2 The platform

All development, training and pre-production work runs on SSP Cloud, the data science platform of the French official statistical system. SSP Cloud is built on the open-source Onyxia project (Avouac et al. 2025). This is possible because Sirene activity descriptions are not sensitive data.

Avouac, Romain, Thomas Faria, and Frédéric Comte. 2025. “A Cloud-Native Data Science Platform for Official Statistics.” In Foundations and Advances of Machine Learning in Official Statistics. Society, Environment and Statistics. Springer. https://doi.org/10.1007/978-3-032-10004-7_8.

Production runs on INSEE’s internal Kubernetes infrastructure. The model is promoted there once it has been qualified on a pre-production platform that matches production.

3 Repositories

The code is organised as a set of single-purpose repositories under the InseeFrLab GitHub organisation:

The repositories do not import one another. They communicate through artifacts:

  • preprocess publishes the location of the latest dataset, along with the feature lists, in a shared configuration file on S3, and train reads it.
  • train logs a self-contained model in MLflow, which embeds its own inference code.
  • api downloads that model at start-up, using a model name and version given as environment variables.
  • cd decides which image, and which model version, each environment runs.

So moving a new model to an environment is a one-line change to a manifest, and it can be reviewed like any other code change.

5 Development workflow

The team works in an umbrella repository, codif-ape, which gathers all the repositories above as Git submodules that track the main branch. It is a workspace, not a release unit: each repository keeps its own version tags and its own CI.

All repositories follow the same conventions:

  • uv for Python environments;
  • pre-commit with ruff for code quality;
  • Renovate for dependency updates;
  • GitHub Actions for building images and documentation.
