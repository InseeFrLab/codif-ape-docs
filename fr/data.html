1 Données d’entraînement

Le modèle apprend sur les déclarations passées, conservées dans le répertoire Sirene. Chaque observation contient :

  • le libellé d’activité : texte libre saisi par le déclarant, parfois complété de précisions sur une activité secondaire ou agricole ;
  • des variables annexes issues du formulaire de déclaration :
    • la catégorie juridique (CJ) ;
    • la nature de l’activité (NAT) ;
    • le type de liasse (TYP) ;
    • la surface du local (SRF, regroupée en tranches) ;
    • le caractère permanent ou saisonnier de l’activité (CRT) ;
  • le code APE attribué, automatiquement ou par un gestionnaire.

Les premiers modèles ont été entraînés sur environ 10 millions de déclarations issues de l’ancien répertoire (2014–2022). Depuis le passage au nouveau répertoire et à la NAF 2025, la base d’entraînement compte environ 2,7 millions de déclarations récentes (Randriamanana et Faria 2025).

AvertissementLes labels ne sont pas une vérité terrain

Les labels historiques viennent de Sicore, des versions précédentes du modèle et de gestionnaires qui travaillent dans l’urgence. Certains sont faux, d’autres se contredisent : un même libellé peut avoir des codes différents. La qualité des labels compte autant que l’architecture du modèle. Deux outils s’en occupent : le moteur de règles (ci-dessous) et les campagnes d’annotation (Monitoring).

2 Nettoyage des labels : un moteur de règles auditable

codif-ape-preprocess applique des règles métier aux données avant chaque entraînement. Une règle, c’est un savoir des experts métier traduit en code. Par exemple, les locations meublées désignées par le sigle « LMNP », les holdings, les chauffeurs VTC et les taxis sont chacun envoyés vers un code précis.

Une règle peut faire trois choses :

Les règles sont des fonctions Python enregistrées via un décorateur, chacune avec un nom, des tags et une description. Pour repérer les libellés concernés, une règle utilise une ou plusieurs de ces trois méthodes :

  • des regex sur le texte normalisé ;
  • du fuzzy matching, pour absorber les fautes de frappe ;
  • de la similarité sémantique, avec un modèle d’embeddings de phrases qui tourne sur GPU.

Le fuzzy matching et la similarité sémantique étendent une règle aux libellés proches de ceux listés par les experts. Chaque règle choisit les méthodes qu’elle autorise : une règle sur un sigle court, par exemple, se limite au match exact.

Le moteur de règles a donc deux volets, qui ne s’évaluent pas de la même façon :

  • le volet déterministe (patterns exacts validés par les experts) encode les cas connus, notés \(K_n\) dans le protocole de réentraînement. Il se vérifie comme un test unitaire : le modèle doit le reproduire ;
  • le volet probabiliste (extensions par fuzzy matching et similarité sémantique) fait un pari sur des libellés qu’aucun expert n’a vus. C’est un moteur de codification automatique à part entière, dont la qualité doit être mesurée avant d’en garder les codes.

Chaque modification est loggée. Pour chaque ligne modifiée, créée ou supprimée, on garde le code avant et après, la règle appliquée et le contexte de la déclaration. Ces logs sont stockés à côté du jeu de données nettoyé, si bien qu’on peut remonter à l’origine de n’importe quel label du jeu d’entraînement.

Les règles rendent durables les retours des experts. Une erreur corrigée seulement par réentraînement peut revenir avec le modèle suivant. Une règle, elle, corrige une fois pour toutes l’ensemble du jeu d’entraînement, et la correction est traçable. La création, la vérification et la propagation des règles sont décrites dans le protocole de réentraînement.

3 Splits et versionnage

Après nettoyage, le pipeline :

  1. construit les variables finales : le libellé concaténé avec ses champs texte complémentaires, et les variables catégorielles ;
  2. découpe les données en jeux d’entraînement, de validation et de test ;
  3. écrit ces jeux sur S3, dans un dossier nommé d’après la date d’extraction ;
  4. référence ce dossier, avec la liste des variables, dans un fichier de configuration partagé que lit le code d’entraînement.

Chaque entraînement logge ses jeux de données d’entrée dans MLflow : on sait donc exactement sur quel snapshot des données il a tourné.

4 Le passage à la NAF 2025

La révision européenne de la nomenclature d’activités (NACE Rév. 2.1, NAF 2025 en France) s’applique à toutes les unités de Sirene au 1er janvier 2027. Il faut donc entraîner le modèle dans une nomenclature dans laquelle aucune donnée historique n’a été codée.

4.1 Le problème de la table de passage

La table de passage officielle entre la NAF rév. 2 et la NAF 2025 relie 732 anciennes sous-classes à 746 nouvelles (Randriamanana et Faria 2025) :

Randriamanana, Nathan, et Thomas Faria. 2025. Changement de nomenclature statistique à l’ère du Machine Learning : réentraînement basé sur les LLM pour la révision de la NAF. Journées de méthodologie statistique (JMS). https://inseefrlab.github.io/codif-ape-prez/papers/jms2025-llm-relabeling/index.pdf.
  • 551 correspondances univoques : l’ancien code donne un seul nouveau code, le passage est mécanique ;
  • 181 correspondances multivoques : l’ancien code éclate en plusieurs nouveaux codes (jusqu’à 38), et il faut lire le libellé pour choisir.

Les codes multivoques ne font que 25 % des codes, mais 52 % des observations d’entraînement, soit environ 1,4 million de lignes. Les experts métier ont d’abord requalifié des « faux multivoques », où une cible domine nettement, ce qui en a réglé environ un tiers. Restaient tout de même environ 500 000 observations à recoder une par une.

4.2 Les experts comme référence, les LLM pour le volume

Le recodage a combiné expertise humaine et LLM :

  1. Annotation par les experts. Environ 25 experts métier ont annoté quelque 30 000 libellés multivoques en NAF 2025, dans Label Studio, pendant environ cinq mois. La campagne a aussi permis de mesurer l’accord inter-annotateurs, ce qui donne un plafond réaliste : trois experts indépendants ne tombent d’accord sur la sous-classe que dans environ 62 % des cas, alors qu’au moins deux d’entre eux sont d’accord dans 96 % des cas.
  2. Les LLM comme annotateurs virtuels. Des LLM open-weight, servis sur la plateforme avec vLLM, ont recodé les observations multivoques (codif-ape-nace-revision). Chaque prompt contenait le libellé, les codes NAF 2025 candidats et leurs notes explicatives, directement dans le contexte, avec une sortie contrainte par un schéma JSON. Plusieurs modèles ont été comparés aux annotations des experts : le meilleur atteignait environ 72 % d’accuracy au niveau sous-classe, et combiner plusieurs modèles, par vote ou en cascade, faisait gagner quelques points.
  3. Des règles métier ont ensuite été appliquées par-dessus, via le moteur de règles, pour corriger les erreurs systématiques.

Au total, environ 2,3 millions des 2,7 millions d’observations ont pu être recodées en NAF 2025. Par la suite, des modèles open-weight plus récents et un vote majoritaire ont fait monter l’accuracy des LLM à environ 78 % (Pramil 2026).

Pramil, Julien. 2026. When Classifications Change but Deadlines Don’t: Scaling Recoding with LLMs. The NACE Transition at Insee. ISI World Statistics Congress, Malta. https://inseefrlab.github.io/codif-ape-prez/slides/isi-malta-relabeling/.
AstuceEnseignement

Les annotations d’experts coûtent cher : mieux vaut s’en servir comme référence, pour choisir les prompts et les modèles et pour mesurer le résultat, et laisser le volume aux LLM. La confiance qu’un LLM déclare lui-même s’est révélée un mauvais filtre ; l’accord entre plusieurs modèles est un bien meilleur signal.

Le modèle réentraîné sur ces données est présenté dans le chapitre Modèle.

5 GRAAL

GRAAL (documentation), Graph-based Reasoning Agents for Automatic Labelling, est un framework d’agents LLM qui codent du texte libre dans une nomenclature hiérarchique. Il repose sur deux briques :

  1. la notice sous forme de graphe, stockée dans la base de données orientée graphe Neo4j (Neo4j, Inc. 2026) ;
  2. des tools que les LLM appellent pour interroger ce graphe.
Neo4j, Inc. 2026. Neo4j: graph database. https://neo4j.com/docs/.

Comme torchTextClassifiers, il est né des besoins de la codification APE et est développé comme un outil généraliste et open source. Mais contrairement à elle, GRAAL est hors du chemin critique : il travaille hors ligne, sur des données, pas sur des requêtes en temps réel. Il a sa place dans ce chapitre parce qu’il produit des codes.

5.1 Principe

Le graphe. La notice complète est chargée dans Neo4j :

  • les codes et leurs libellés ;
  • les notes explicatives : inclusions, exclusions, exemples ;
  • les relations parent–enfant, ainsi qu’un index vectoriel sur les notes.

Les tools. Les LLM n’accèdent au graphe que via des tools : descendre ou remonter la hiérarchie, lire les notes d’un code, chercher les notes les plus proches d’un texte. Ils parcourent ainsi la nomenclature comme le ferait un expert humain. Les agents décrits plus bas ne sont que des façons différentes de combiner ces tools. Toutes les entrées et sorties sont des modèles Pydantic typés. Les agents marchent avec n’importe quel endpoint compatible avec l’API OpenAI ; sur la plateforme, ce sont des modèles open-weight.

Comme tout ce qu’il faut savoir de la nomenclature est dans le graphe, le framework est indépendant de la nomenclature. Des graphes existent pour la NAF 2025 (en français), la NACE Rev. 2.1 (en anglais) et la COICOP 2018.

5.2 Les agents

GRAAL comprend aussi un module d’évaluation et des applications de revue où les experts métier jugent les verdicts des agents. Le module d’évaluation fournit des métriques à chaque niveau, des échantillons stratifiés pondérés, des intervalles de confiance par bootstrap et des tests appariés.

5.3 Rôle dans le pipeline

GRAAL ne remplace pas le modèle de production. Les agents mettent de quelques secondes à quelques minutes par libellé et ont besoin de GPU pour le LLM, alors que la production demande environ 200 ms sur CPU. Sur les premiers benchmarks, ils ne faisaient d’ailleurs pas mieux que le modèle supervisé sur l’ensemble du flux. L’intérêt de GRAAL est ailleurs, dans quatre tâches hors ligne :

  1. Recoder un stock après un changement de nomenclature. L’essentiel des données d’entraînement NAF 2025 a été produit par un pipeline dédié, codif-ape-nace-revision, dans laquelle des LLM codent avec les notes explicatives dans leur contexte (voir plus haut). GRAAL généralise cette approche avec des agents qui naviguent dans la nomenclature, pour les révisions futures et pour d’autres nomenclatures.
  2. Auditer et fiabiliser les codes. Le MatchVerifier repère les codes douteux dans les données d’entraînement ou parmi les cas codés automatiquement, et propose des alternatives. Dans le protocole de réentraînement, GRAAL est l’un des moteurs indépendants dont les désaccords avec le modèle de production sont arbitrés.
  3. Prioriser la revue humaine. Les cas suspects passent en priorité devant les experts métier, dont les avis, recueillis dans une application de revue, deviennent de nouvelles annotations.
  4. Générer des données synthétiques. Code2Text produit des libellés pour les codes rares (voir plus bas), ainsi que des variantes reformulées de cas connus, pour vérifier qu’une correction se généralise.

En retour, GRAAL s’appuie sur l’API de production, comme baseline supervisée et comme source de codes candidats pour les agents et les annotateurs.

5.4 Des codes qui doivent faire leurs preuves

GRAAL et la partie probabiliste du moteur de règles jouent le même rôle : ils proposent des codes qu’aucun humain n’a vérifiés. Avant que l’un ou l’autre n’alimente l’entraînement, on l’évalue là où ça compte : sur les cas où il n’est pas d’accord avec le modèle de production, par rapport au golden set. Le critère et ses précautions sont détaillés dans le protocole de réentraînement et dans le chapitre Évaluation.

6 Données synthétiques : Code2Text

Pendant son stage au SSP Lab (ENSAE Paris, 2026), Matéo Morin a travaillé sur la génération de libellés synthétiques par LLM pour la NAF 2025, dans le prolongement de l’agent Code2Text de GRAAL. Rapport, slides et annexes : mateomorin.github.io/Code2Text-presentation. Ces travaux restent exploratoires.

6.1 Pourquoi générer des libellés

Deux motivations :

  • les codes rares : sur plus d’un million de libellés d’entraînement, la moitié des codes ont moins de 60 exemples, et le modèle les apprend mal ;
  • le secret statistique : impossible de diffuser les déclarations, que ce soit pour des cours, des hackathons ou de la recherche. Un jeu synthétique assez réaliste, lui, pourrait l’être.

Les deux usages n’appellent pas la même distribution des codes : pour diffuser, il faut coller à la distribution réelle ; pour entraîner, on a intérêt à surreprésenter les codes rares. On génère donc code par code. Si, pour un code donné, les libellés générés ressemblent aux vrais, il ne reste qu’à choisir combien en tirer par code selon l’usage visé.

6.2 Une première version : NaiveCode2Text

Pour chaque code, on donne au LLM son intitulé, une partie des inclusions, toutes les exclusions et quelques vrais libellés du même code en exemple (few-shot). Les appels sont parallélisés : 62 100 libellés couvrant toute la nomenclature en 42 minutes.

Sur le fond, les libellés tiennent la route. Mais ils sont trop propres : pas de fautes, un ton très formel, souvent proche de l’intitulé du code. Pour la sylviculture, on obtient par exemple « Activités forestières : culture de peupliers et de saules ». Demander dans le prompt un style plus relâché n’y change rien.

6.3 Un texte de LLM, ça se repère : LabelGuard

LabelGuard est un classifieur qui distingue un libellé écrit par un déclarant d’un libellé généré. C’est un MLP sur les embeddings de Qwen3-Embedding-8B, entraîné sur 160 000 libellés, moitié vrais, moitié synthétiques. On a d’abord retiré des vrais libellés ce qui les trahit trop facilement (troncature à 140 caractères, numéros, suffixe ajouté au prétraitement), pour qu’il apprenne le style et pas ces artefacts.

Résultat : 99,4 % d’accuracy sur 40 000 libellés de validation, pour 0,7 % de faux positifs. Le style d’un LLM se repère donc presque à coup sûr. Pour le classifieur, c’est du covariate shift : entraîné sur ces libellés, il ne voit pas le même texte qu’en production, où les libellés sont abrégés, télégraphiques et pleins de fautes.

6.4 Casser le style : Code2ReText

Premier essai : donner directement LabelGuard en tool au LLM générateur. Il a vite triché : mots collés, mots inventés, et copie pure et simple des libellés qui passaient le test.

La version retenue, Code2ReText, répartit le travail entre deux LLM, orchestrés avec LangGraph :

  • l’Acteur génère des libellés comme NaiveCode2Text, puis les reformule. Il peut changer la forme, pas le fond ;
  • le Superviseur voit les scores de LabelGuard et de vrais libellés du même code. Il dit à l’Acteur comment réécrire ceux qui se font repérer (score supérieur à 0,70), sans lui montrer les vrais libellés.

Cinq tours au maximum. Le score moyen de LabelGuard baisse à chaque tour. Pour la sylviculture, on obtient désormais par exemple « TRANSPLANTATION ARBRES ».

6.5 Résultats

Un classifieur aux hyperparamètres fixés (choisis sur données réelles) est entraîné sur des jeux de 50 000 libellés comprenant une part \(\alpha\) de synthétique, puis évalué sur 30 000 vrais libellés. Les jeux sont emboîtés : les libellés synthétiques utilisés pour un \(\alpha\) donné se retrouvent dans tous les jeux à \(\alpha\) plus élevé, et chaque code apparaît au moins une fois. Les écarts d’un \(\alpha\) à l’autre ne viennent donc pas de l’échantillonnage.

  • Accuracy globale. Elle tient jusqu’à environ 50 % de synthétique et s’effondre au-delà de 90 %.
  • Selon la fréquence du code. Rien ne bouge sur les codes fréquents. Sur les codes de fréquence intermédiaire, l’accuracy baisse quand \(\alpha\) augmente. Sur les codes rares, elle progresse nettement dès les premiers ajouts, surtout avec Code2ReText. Le bon compromis se situe autour de 40 à 50 % de libellés Code2ReText, tirés selon une distribution des codes proche de la réalité.
  • Style contre diversité. Pour presque tous les codes, Code2ReText est plus proche des vrais libellés que NaiveCode2Text (distance de Wasserstein entre embeddings). Mais sa diversité (DC-Score) s’effondre, alors que celle de NaiveCode2Text dépasse même un peu celle des vrais libellés. On n’a pas les deux à la fois.
  • Recopie. Environ 0,5 % des libellés de Code2ReText sont des copies de vrais libellés, contre 0,005 % pour NaiveCode2Text : l’Acteur et le Superviseur ont trouvé là un autre moyen de tromper LabelGuard. En l’état, c’est rédhibitoire pour une diffusion.

Ces résultats portent sur 50 000 libellés, pas sur le million de la base complète, et héritent du bruit des vrais labels (voir plus haut). Piste suivante : plutôt que de corriger le style à coups de boucles de prompts, faire un fine-tuning d’un petit modèle open-weight sur la façon d’écrire des déclarants. Le même modèle pourrait générer des libellés NACE dans plusieurs langues.

AstuceEnseignement

Le synthétique complète les vraies données sur les codes rares, il ne les remplace pas. Un LLM a un style qui se repère : mieux vaut le mesurer avant d’injecter quoi que ce soit. Et un générateur optimisé pour tromper un discriminateur finit par recopier ses exemples : avant toute diffusion, il faut vérifier qu’aucun vrai libellé n’a fuité.
