1 Principes de conception

La chaîne repose sur quelques principes, partagés avec le cadre MLOps européen élaboré dans le projet AIML4OS (Tayebjee et al. 2025) :

Tayebjee, Meilame, Nina Niederhametner, Bogdan Levagin, et Ariane Lestrade. 2025. From text to code (WP10.4) – MLOps tutorial. AIML4OS project, Work Package 10. https://aiml4os.github.io/WP10_Cluster4_MLOps/.
  • Séparer données, code et calcul.
    • Les données sont stockées au format Parquet, dans un stockage objet S3.
    • Le code est versionné dans Git.
    • Le calcul est assuré par des conteneurs lancés à la demande.
  • Tout rendre reproductible.
    • Chaque entraînement est piloté par un fichier de configuration.
    • Chaque environnement est figé (fichiers de verrouillage uv, images Docker).
    • Chaque jeu de données, chaque modèle et chaque image est versionné.
  • Empaqueter le modèle avec son prétraitement, pour que ce qui a été évalué soit exactement ce qui est servi (pas d’écart entre entraînement et service, le training/serving skew).
  • Décrire les déploiements de façon déclarative. L’état de chaque environnement est un ensemble de manifestes stockés dans Git. Un contrôleur GitOps aligne le cluster sur ces manifestes.
  • Garder l’humain dans la boucle. Les prédictions peu sûres partent en reprise manuelle, et c’est l’annotation humaine qui mesure la qualité.

2 La plateforme

Le développement, l’entraînement et la préproduction se font entièrement sur le SSP Cloud, la plateforme de data science du service statistique public français. Le SSP Cloud repose sur le projet open source Onyxia (Avouac et al. 2025). Ce choix est possible parce que les libellés d’activité de Sirene ne sont pas des données sensibles.

Avouac, Romain, Thomas Faria, et Frédéric Comte. 2025. « A Cloud-Native Data Science Platform for Official Statistics ». In Foundations and Advances of Machine Learning in Official Statistics. Society, Environment et Statistics. Springer. https://doi.org/10.1007/978-3-032-10004-7_8.

La production tourne sur l’infrastructure Kubernetes interne de l’Insee. Le modèle n’y est promu qu’après avoir été qualifié sur une plateforme de préproduction identique à la production.

3 Dépôts

Le code est organisé en dépôts à vocation unique, regroupés dans l’organisation GitHub InseeFrLab :

Les dépôts ne s’importent pas les uns les autres. Ils communiquent par des artefacts :

  • preprocess publie l’emplacement du dernier jeu de données, avec les listes de variables, dans un fichier de configuration partagé sur S3 ; train lit ce fichier.
  • train enregistre dans MLflow un modèle autonome, qui embarque son propre code d’inférence.
  • api télécharge ce modèle au démarrage, à partir d’un nom et d’une version de modèle passés en variables d’environnement.
  • cd détermine l’image, et la version du modèle, que fait tourner chaque environnement.

Déployer un nouveau modèle dans un environnement revient donc à modifier une ligne d’un manifeste. Cette modification se relit comme n’importe quelle autre modification de code.

4 Flux de bout en bout

Chaque bloc est détaillé dans un chapitre dédié :

  • Données : sources, nettoyage des labels et passage à la NAF 2025.
  • Modèle : architecture, entraînement et évaluation.
  • Mise à disposition et déploiement : empaquetage, API et GitOps.
  • Suivi et annotation : boucler la boucle.
  • Protocole de réentraînement : comment la boucle aboutit, sans risque, à un nouveau modèle.

5 Organisation du développement

L’équipe travaille dans un dépôt parapluie, codif-ape, qui rassemble tous les dépôts ci-dessus sous forme de sous-modules Git suivant la branche main. C’est un espace de travail, pas une unité de livraison : chaque dépôt garde ses propres tags de version et sa propre intégration continue.

Tous les dépôts suivent les mêmes conventions :

  • uv pour les environnements Python ;
  • pre-commit avec ruff pour la qualité du code ;
  • Renovate pour la mise à jour des dépendances ;
  • GitHub Actions pour la construction des images et de la documentation.
