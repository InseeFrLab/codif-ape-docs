Mise en production

Un modèle autonome, une API légère et un déploiement en GitOps.
Auteur
Affiliation

1 Un modèle autonome

Le modèle est enregistré dans MLflow sous forme de pyfunc, un wrapper Python générique qui embarque tout ce qu’il faut pour l’inférence :

  • le réseau entraîné et son tokenizer ;
  • les encodeurs des variables catégorielles et des classes ;
  • le code d’inférence : validation de la liasse en entrée, construction des variables, décodage du top k avec les intitulés des codes, calcul de l’indice de confiance ;
  • les ressources nécessaires hors ligne, comme les listes de stop words, pour que rien ne soit téléchargé à l’exécution dans un environnement fermé.

Le contrat d’entrée et de sortie est défini par des modèles Pydantic dans le dépôt d’entraînement. Le modèle se charge et s’appelle donc de la même façon dans un notebook, dans un job batch ou dans l’API, et le modèle servi est exactement celui qui a été évalué.

Chaque modèle enregistré porte un nom, qui identifie la nomenclature (NAF rév. 2 ou NAF 2025), et une version. Chaque réponse contient l’identifiant du modèle qui l’a produite, ce qui rend toute prédiction traçable.

2 L’API

codif-ape-api est une application FastAPI légère. Au démarrage, elle charge le modèle à partir de son nom et de sa version, passés en variables d’environnement. Elle expose un seul endpoint de prédiction :

  • Entrée : un batch de liasses. Chacune contient un libellé d’activité obligatoire et des champs annexes optionnels : forme juridique, nature de l’activité, type de liasse, surface, permanence de l’activité. Les valeurs sont validées par rapport aux modalités autorisées avant l’inférence.
  • Sortie : pour chaque liasse, le top k des codes avec leur probabilité et leur intitulé, l’indice de confiance et l’identifiant du modèle.
  • Paramètres : le nombre de propositions, une probabilité minimale, la taille des batchs et le nombre de processus. Le même endpoint sert donc à la fois les appels unitaires du répertoire (une liasse à la fois, latence minimale) et les recodages en masse (gros batchs traités en parallèle).

L’API utilise des builds PyTorch CPU uniquement et n’écrit ses logs que sur la sortie standard, comme l’exige la plateforme de production. C’est le seul composant appelé par le système d’information Sirene : l’application Java qui gère les déclarations envoie la liasse à l’API, puis l’aiguille selon l’indice de confiance.

3 CI/CD

Le déploiement fonctionne ainsi :

  1. Images. À chaque push sur main et à chaque tag de version, GitHub Actions build l’image Docker de l’API et la pousse sur le registry. Sur chaque pull request, on vérifie que l’image build.
  2. Manifestes. codif-ape-cd contient les manifestes Kubernetes bruts de tous les services :
    • les instances de l’API, pour chaque nomenclature et chaque environnement ;
    • le dashboard de monitoring ;
    • les cron jobs d’annotation et de monitoring ;
    • les applications de revue de GRAAL.
  3. Synchronisation. Chaque dossier du dépôt a son Application Argo CD, avec auto-sync et self-heal activés : le cluster reflète toujours le contenu du dépôt.

Déployer un nouveau modèle revient à modifier une ligne d’un manifeste : la version du modèle, ou le tag de l’image si le code de l’API a changé. Le changement est relu et mergé, puis Argo CD le déploie. Pour revenir en arrière, il suffit de revert ce commit. L’historique de ce qui a tourné, où et quand, c’est le log Git.

4 Environnements

Plusieurs instances de l’API tournent en parallèle sur la plateforme, chacune identifiée par sa nomenclature et sa génération de modèle, par exemple un modèle NAF 2008 et un modèle NAF 2025 en PyTorch. Elles servent :

  • au développement et aux démonstrations ;
  • à comparer les générations de modèles sur les mêmes entrées ;
  • aux recodages en masse.

Avant la production, le modèle passe par une qualification sur une préproduction identique à la production (voir Défis organisationnels et d’infrastructure) :

  • on mesure la latence et la mémoire sur CPU ;
  • on vérifie la cohérence online/offline : le modèle servi doit reproduire exactement les prédictions de l’évaluation hors ligne ;
  • une période en shadow mode peut suivre : le nouveau modèle traite le flux réel sans que ses décisions soient utilisées.

Ces étapes sont détaillées dans le protocole de réentraînement.
